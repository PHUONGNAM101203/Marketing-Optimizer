## Architecture

Next.js 16 App Router + Supabase (Postgres, RLS, `service_role` for background writes) + TypeScript. Every marketing channel (Google Ads, GA4, Search Console, Tag Manager, YouTube, Merchant Center, Meta Ads, Instagram, Facebook, TikTok) is modeled uniformly through three layers in `src/lib/`:

- **`providers/`** — one file per platform's raw API calls (OAuth token exchange, discovery, metrics fetch). No knowledge of Supabase or the app's data model.
- **`data/`** — reads/writes through Supabase, calling into `providers/` for anything live. Functions here are what pages/actions actually call.
- **`sync/`** — the write path: `sync-connection.ts`'s `syncConnection(connectionId)` is the single entry point that refreshes a connection's tokens and metrics; it's invoked from the daily cron, the OAuth callback, and manual resync actions alike. Anything that must run "whenever a connection is (re)synced" belongs here.
- **`actions/`** — `'use server'` Server Actions, the mutation surface called from client components/forms.
- **`domain/`** — plain types and pure logic shared across the above, no I/O.

### Provider model (`src/lib/domain/providers.ts`)

`PROVIDERS` (10 platforms) each belong to a `ProviderFamily` (`'google' | 'youtube' | 'meta' | 'tiktok'`) and declare `capabilities` (`spend`/`traffic`/`conversions`/`rankings`/`content`/`tagging`/`catalog`). UI components read `capabilities` to decide what to render instead of branching per-provider — adding a platform is primarily adding a `PROVIDERS` entry plus its `providers/`/`data/`/`sync/` files, not touching every consumer.

`ProviderFamily` matters because OAuth is per-family, not per-provider: one Google OAuth grant can back GA4 + Search Console + Tag Manager + Merchant Center + Google Ads simultaneously (`src/app/api/oauth/[family]/{start,callback}/route.ts`), and a site can connect a *different* Google account for YouTube specifically (YouTube is its own family so it doesn't have to share the primary Google grant). When a provider needs to borrow another connection's OAuth token instead of doing its own handshake (e.g. selecting a Google Ads account, a specific GTM container), see `findGoogleSourceConnection`/`copyConnectionSecret` in `src/lib/data/`.

### Metrics: two shapes, two tables

- **`metrics_daily`** — one row per `(connection_id, date)`, the common shape (`sessions`/`users`/`conversions`/`clicks`/`impressions`/`cost_micros`/`conversion_value_micros` + a `extra` jsonb for platform-specific fields) that every `MetricsAdapter` in `providers/metrics-types.ts` normalizes into, regardless of source platform. Written by `syncConnection`.
- **`video_metrics_daily`** — one row per `(connection_id, external_video_id, date)`, TikTok-only. TikTok's API only exposes *cumulative* per-video counters with no historical report, so growth has to be computed by diffing our own daily snapshots (`src/lib/sync/sync-video-snapshots.ts`). YouTube doesn't need this table — YouTube Analytics accepts arbitrary date ranges directly, so `src/lib/providers/google-explore.ts`'s `getYoutubeVideoTrending` queries it live instead of storing anything. Both still expose the same `VideoTrendingResult` shape (`src/lib/providers/video-trending-types.ts`) so the channel-detail UI doesn't need to know which platform is which.

`getChannelDetail` (`src/lib/data/site-channel-detail.ts`) is the read path both metrics shapes feed into: a discriminated union (`ChannelDetail`, keyed by `kind`) with one variant per provider, built from a switch statement in `getChannelDetail`. Extending it for a new provider or a new field means adding one union member and one switch case — not touching the others.

### RLS pattern

Every table follows the same split: normal tables (`connections`, `metrics_daily`, `video_metrics_daily`, ...) allow `select` for `authenticated` users gated by `is_site_member(site_id)` (a Postgres function checking `site_members`), and have **no write policy** — writes only happen via the `service_role` key from server-side code (`createAdminClient()`), never from a user session. `connection_secrets` (encrypted OAuth tokens) has no policies for any role at all; only `service_role` can touch it. New tables should follow this shape unless there's a specific reason not to.

### Background sync

`src/app/api/cron/sync-all/route.ts` is the only cron job (Vercel Hobby plan = one cron job, run once daily — do not add a second cron; extend `syncConnection` or gate new work behind a flag instead). It loops every connection and calls `syncConnection`. Time-sensitive work that must run for every connection (like the TikTok video snapshot) is wired into `syncConnection` itself rather than getting a separate schedule, and is wrapped in Next's `after()` where it doesn't need to block the caller's response (see the TikTok snapshot call site in `sync-connection.ts` for the pattern — `after()` needs to be called from live request scope, which every one of `syncConnection`'s six call sites provides).

### Code conventions specific to this repo

- Comments are Vietnamese and explain only the non-obvious *why* (a constraint, a workaround, a decision that would otherwise look arbitrary) — never restate what the code does. This is enforced by convention, not tooling; match the surrounding file's style.
- Adapters/providers document API assumptions that haven't been verified against a real token/account yet with a header comment (search for "CHƯA ai chạy thử" to find these) — when adding a new unverified integration, follow the same pattern rather than presenting guessed behavior as confirmed.
- No mocked-out feature flags or dead abstractions for platforms that aren't implemented yet — a provider either has real `providers/`/`data/`/`sync/` code or it doesn't appear as connectable.

### Multi-tenant shell (`src/app/(app)/[siteId]/`)

Every page under this segment is scoped to one site. Its `layout.tsx`
resolves `site`/`profile`/`connections` once per request and renders the
shared `SideRail` + `Topbar` around all children. A site that's missing *or*
merely inaccessible both return `notFound()`, never a 403 — Supabase RLS
already filtered it, and a 403 would confirm the site's existence to someone
without access to it. Follow the same non-distinguishing-404 convention for
any new site-scoped resource.

### `lib/data/` vs `mock/`

`src/lib/data/*` reads real Supabase tables; `src/mock/*` is leftover
milestone-1 sample data for pages not yet migrated off it. Treat `mock/` as
scaffolding to delete, not a pattern to extend — if a page still reads from
`mock/`, that means its real data layer doesn't exist yet, not that mock
data is the intended long-term source.

### Design system (Hallmark — "Ink & Signal")

`src/lib/design/tokens.css` is the only place colors (OKLCH), spacing, radii,
type scale, and motion values are defined, for both light and dark
(`prefers-color-scheme` and an explicit `data-theme` override).
`src/app/globals.css` imports it and the convention is that **no raw
hex/oklch/font-family appears anywhere outside `tokens.css`** — everything
else resolves through a token. One accent color only (`--color-signal`, kept
to a small footprint); a fixed 9-slot chart palette assigned per provider via
`colorToken` in `PROVIDER_META` — don't reorder/reassign those slots.

Primitives live in `src/components/ui/` (shadcn-style: `card`, `button`,
`dialog`, `table`, `stat-tile`, `delta`, `pagination`, `badge`, `feedback`,
date/time pickers). Most components across `src/components/**` carry a
header comment `/* Hallmark · component: <name> · theme: studied-DNA (Ink &
Signal) */` — keep that convention on new components.

### Date ranges

`src/lib/domain/site.ts` defines `DateRangePreset` (`last-7` / `last-28` /
month / `custom`); `src/mock/dates.ts`'s `resolveDateRange` turns a preset
into concrete start/end plus previous-period bounds for deltas.
`src/lib/domain/date-range-param.ts` parses the `range`/`from`/`to` URL
search params. Pages read the date range from `searchParams` server-side —
not client `useState` — so it's bookmarkable, shareable, and works from
Server Components. Follow this pattern for any new filter/tab/view-state that
should behave the same way, rather than local `useState`.
